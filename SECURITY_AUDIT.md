# LLM CostOpt — Security Audit & Penetration Report

This document summarizes the methodology, findings, exploits checked, and remediations executed during the security review of the LLM CostOpt platform.

An automated attack audit script was created at [`scripts/security_test.py`](file:///c:/Users/Lenovo/Downloads/DS%20mini%20project/scripts/security_test.py) to simulate attacks against the API.

---

## 1. Audit Scope & Checked Loophole Vectors

### A. SQL Injection (SQLi)
- **Vulnerability Check**: Attempted to inject SQL syntax commands (e.g. `' OR '1'='1`, `'; DROP TABLE;`) into the API query parameters (`env`, `z_score`) to see if the database interpreter would execute unauthorized queries or leak table rows.
- **Audit Outcome**: **SECURE (PASSED)**. 
  - FastAPI automatically enforces parameter type-casting (e.g. `z_score` must be a float, invalid strings return `422 Unprocessable Content`).
  - All direct SQL queries in [`src/costopt/api/routes.py`](file:///c:/Users/Lenovo/Downloads/DS%20mini%20project/src/costopt/api/routes.py) utilize parameterized sql query templates (`?` placeholder bindings).

### B. Cross-Origin Resource Sharing (CORS) Misconfiguration
- **Vulnerability Check**: Simulated a cross-origin credentialed request from a malicious external domain (`Origin: http://evil-attacker.com`) querying local endpoints.
- **Audit Outcome**: **VULNERABLE (HOTFIXED)**.
  - *The Loophole*: Originally, [`src/costopt/api/server.py`](file:///c:/Users/Lenovo/Downloads/DS%20mini%20project/src/costopt/api/server.py) set CORS origins to `allow_origins=["*"]` with `allow_credentials=True`. This could allow cross-origin reads of the local metrics DB by external websites visited by the developer.
  - *Remediation*: Hotfixed the CORS origin list to only allow trusted local client domains (`allow_origins=["http://localhost:8000", "http://127.0.0.1:8000"]`). Re-running the attack script confirms that requests from untrusted origins are blocked (`Access-Control-Allow-Origin: None`).

### C. Rate Limiting & Concurrency DB Lock (Denial of Service)
- **Vulnerability Check**: Stress-tested the database and API layer by sending rapid concurrent requests to evaluate if SQLite's single-write file lock locks read endpoints, causing thread exhaustion.
- **Audit Outcome**: **SECURE (PASSED)**.
  - The API successfully resolved 50 concurrent requests in 0.13s with zero failures.
  - *Architectural Resiliency*: The telemetry logger in [`src/costopt/telemetry.py`](file:///c:/Users/Lenovo/Downloads/DS%20mini%20project/src/costopt/telemetry.py) utilizes a thread-safe in-memory queue to flush database writes asynchronously in batches, which prevents write operations from blocking the main API thread or locking the read-replica sqlite database during high API traffic.

## 3. Production Security Hardening Recommendations

To ensure safety in production environments, developers should adopt these best practices:

1. **Disable Local CORS**: When deploying in production, disable CORS entirely or restrict it to the reverse-proxy domain.
2. **Prompts Sanitation**: By default, LLM CostOpt generates prompt hashes for caching. If you decide to store raw prompt texts, configure strict Access Control lists (ACLs) on the SQLite database files to prevent unauthorized system reads.
3. **Database Security**: Keep the `costopt_telemetry.db` and `costopt_cache.db` files in a restricted subfolder of the application workspace with `chmod 600` permissions.
